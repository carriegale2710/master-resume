## **No-bullshit CV checklist specific by the role**

* Build **one master CV per role type** using the relevant section above.

---

## **0\. Universal Rules (All Roles)**

Tick these before anything else.

* Pick one stack/role and say it clearly.  
* Show skills inside projects/experience, not in a big “Skills” list.  
* For every bullet: what you did, how you did it, why it mattered (business impact).  
* Keep formatting simple, one column, and ruthlessly relevant to the job.  
* **Every bullet \= what \+ how \+ why (impact)** in 1–2 lines.  
* **Top third of page 1** shows: role, stack, 1–2 strongest projects/internships with impact.  
* **One target role per CV** (e.g. “Junior Full‑Stack SWE”, not “Open to anything”).  
* **Headline states your stack/role** in plain language.  
* **One page**, single‑column, no tables/graphics in the body. Use Calibri font only.  export as a word doc always.  
* **No generic “Skills” section**; tech appears inside projects/experience bullets.  
* **Links work**: GitHub/portfolio/Live demos/LinkedIn.  
* **Tailored to the job post**: mirror keywords/tech from the description (truthfully).  
* if its a graduate role, put education & training at the top just under summary, else put at bottom.  
* make sure any links are fully typed out (excluding ‘https://’), not just hyperlinked to a word.  
* For each application:  
  * Mirror the job’s stack/keywords in your headline and project bullets.  
  * Trim anything not directly relevant to that role.  
* Treat the recruiter’s “hamburger vs hot dog” rule literally: if the job wants a full‑stack TS engineer, your CV should read like a hamburger, not a plate of random projects.  
* Make sure wording is concise, specific and easy for non-technical people to understand too (eg. hiring managers, recruiters) but always include any technologies or tech stack / tool or skills used (especially if in job description) 

If any of these fail, stop and fix before role‑specific stuff.

## **3\. QA Tester / Junior SDET**

**Headline example:** “Junior QA Engineer | Manual \+ Automation (Playwright, Cypress, Python)”

### **Must‑have signals**

* **Clear QA focus**: manual testing, test automation, or both.  
* **2–3 testing projects** showing:  
  * Test plans / cases  
  * Automation framework (Playwright/Cypress/Selenium/etc.)  
  * CI integration (GitHub Actions, etc.)

### **Project bullets**

* **What**: what system/app you tested and risk area (e.g. checkout, auth, payments).  
* **How**: tools \+ approach (e.g. “Built E2E suite with Playwright \+ TypeScript, 40+ tests, parallelized in CI”).  
* **Why (impact)**:  
  * “Caught 15+ critical bugs pre‑release”  
  * “Reduced regression cycle from 2 days → 2 hours”  
  * “Increased coverage from 35% → 78%”  
* Show **process understanding**: bug reports, severity/priority, test data management, environment setup.

### **Experience / internships**

* Emphasize QA tasks: test case design, regression runs, automation scripts, bug triage.  
* Metrics: defects found, escape rate, cycle time, flakiness reduction.

### **Formatting specifics**

* Avoid generic “Testing” in skills; show tools inside project bullets (Playwright, Postman, JIRA, etc.).  
* If you have any domain knowledge (fintech, health, e‑commerce), make it explicit in project descriptions.

## **1\. Full‑Stack Software Engineer (Junior)**

**Headline example:** “Junior Full‑Stack Engineer | TypeScript, React, Node, PostgreSQL”

### **Must‑have signals**

* **Stack is explicit and consistent** across headline, projects, and experience.  
* **At least 2 full‑stack projects** showing:  
  * Frontend (React/Next/Vue/etc.)  
  * Backend (Node/Express/FastAPI/Spring/etc.)  
  * Database \+ schema/migrations  
  * Auth \+ deployment

### **Project bullets (for each full‑stack project)**

For 3–5 key projects, ensure each has:

* **What**: 1‑line description of the product and user/problem.  
* **How (tech)**: stack embedded in bullets, e.g. “Built REST API with Node \+ Express \+ PostgreSQL”.  
* **Why (impact)**: at least one metric/outcome, e.g. “cut onboarding time by 40%”, “handled 500 sign‑ups”, “reduced API latency from 450ms → 180ms”.  
* **Depth signals**:  
  * Auth (sessions/JWT/OAuth)  
  * DB design (relations, indexes)  
  * Deployment (Vercel/Render/AWS)  
  * Basic tests/CI

### **Experience / internships**

* Bullets framed as engineering impact, not duties: automation, tooling, APIs, performance, reliability.  
* Metrics wherever possible (time saved, errors reduced, throughput up).

### **Formatting specifics**

* Projects don’t need dates; internships/work do (month/year).  
* No multi‑column layouts; no skill bars/percentages.

## **2\. Front‑End Software Engineer (Junior)**

**Headline example:** “Junior Front‑End Engineer | React, TypeScript, Next.js, Tailwind”

### **Must‑have signals**

* **Front‑end stack is crystal clear**: framework \+ language \+ styling \+ tooling.  
* **2–3 front‑end projects** showing:  
  * Component architecture  
  * State management (React Query/Zustand/Redux/etc.)  
  * API integration  
  * Responsive, accessible UI

### **Project bullets**

* **What**: product \+ user \+ core UX goal.  
* **How**: mention frameworks, patterns, performance work (e.g. “code‑splitting”, “memoization”, “SSR/SSG”).  
* **Why (impact)**: metrics like:  
  * “Improved Lighthouse performance from 62 → 94”  
  * “Reduced initial bundle by 35%”  
  * “Increased conversion by 12% after redesign”  
* Show **accessibility / DX**: a11y checks, component library, Storybook, design system usage.

### **Experience / internships**

* Highlight UI work: component libraries, design handoff, cross‑browser fixes, performance tuning.  
* Quantify: load time improvements, reduced re‑renders, fewer bugs, faster feature delivery.

### **Formatting specifics**

* No giant “Skills” grid; tech appears in project bullets.  
* Portfolio link is prominent and working (case studies \> screenshots).

## **4\. AI Engineer (Junior / LLM‑focused)**

**Headline example:** “Junior AI Engineer | Python, LLMs, RAG, LangChain, Vector DBs”

### **Must‑have signals**

* **AI/LLM stack is explicit**: languages, frameworks, model types, infra.  
* **2–3 AI projects** showing:  
  * Data ingestion / cleaning  
  * Model usage (API or local)  
  * RAG / agents / evaluation  
  * Deployment (API, UI, or integrated app)

### **Project bullets**

* **What**: problem \+ user \+ AI capability (e.g. “RAG chatbot for internal docs”).  
* **How**:  
  * Models (GPT‑4o, Llama 3, etc.)  
  * Frameworks (LangChain, LlamaIndex, etc.)  
  * Vector DB (Pinecone, Qdrant, pgvector, etc.)  
  * Evaluation approach (human eval, automated metrics)  
* **Why (impact)**:  
  * “Reduced support tickets by 25% via self‑serve answers”  
  * “Cut doc search time from 10 min → 30 sec”  
  * “Achieved 85% answer accuracy on eval set”  
* Show **production thinking**: latency, cost control, prompt versioning, logging, basic monitoring.

### **Experience / internships**

* Highlight AI‑adjacent work: data pipelines, evaluation scripts, internal tools for ML/AI teams.  
* Quantify: time saved, accuracy gains, cost reductions, adoption metrics.

### **Formatting specifics**

* No buzzword salad; every AI term appears in a concrete project context.  
* Links to demos/notebooks/repos are working and documented.

## **5\. Product Designer (Junior / UX/UI)**

**Headline example:** “Junior Product Designer | UX Research, Interaction Design, Figma”

### **Must‑have signals**

* **Product design focus is clear**: research → concepts → UI → handoff.  
* **2–3 case studies** showing full process, not just pretty screens.

### **Case study / project bullets**

For each featured project (in CV or portfolio summary):

* **What**: problem, users, constraints, your role.  
* **How**:  
  * Research methods (interviews, surveys, usability tests)  
  * Key insights  
  * Ideation, wireframes, prototypes, iterations  
  * Handoff to devs (specs, components)  
* **Why (impact)**:  
  * “Increased task success rate from 58% → 87%”  
  * “Reduced time‑on‑task by 30%”  
  * “Improved conversion by 15% after checkout redesign”  
* Show **collaboration**: working with PMs, engineers, stakeholders.

### **Experience / internships**

* Emphasize design work: research, flows, UI, design systems, usability testing.  
* Quantify outcomes where possible (metrics, stakeholder feedback, adoption).

### **Formatting specifics**

* CV points to a **strong portfolio**; portfolio does the visual heavy lifting.  
* CV itself stays clean and text‑focused; no big images or multi‑column layouts.

## **6\. Service Designer (Junior)**

**Headline example:** “Junior Service Designer | Journey Mapping, Blueprinting, Co‑Design”

### **Must‑have signals**

* **Service design focus is explicit**: end‑to‑end journeys, touchpoints, ops, policy.  
* **2–3 service projects** showing:  
  * Stakeholder mapping  
  * Journey maps \+ service blueprints  
  * Co‑design workshops  
  * Implementation/impact

### **Project bullets**

* **What**: service, users, channels (digital \+ offline), constraints.  
* **How**:  
  * Research (contextual inquiry, interviews, shadowing)  
  * Mapping (journeys, blueprints, ecosystems)  
  * Co‑design sessions, prototypes, pilots  
  * Handoff to product/ops/policy teams  
* **Why (impact)**:  
  * “Reduced average handling time by 20%”  
  * “Cut drop‑off at onboarding step 3 from 35% → 12%”  
  * “Enabled new channel (SMS) serving 10k+ users/month”  
* Show **systems thinking**: frontstage/backstage, policies, constraints, org impact.

### **Experience / internships**

* Highlight work with cross‑functional teams, operations, policy, or customer service.  
* Quantify improvements in KPIs, NPS, cost, time, error rates.

### **Formatting specifics**

* CV summarizes projects; portfolio/case studies show maps/blueprints.  
* Keep CV one page, text‑first; no complex diagrams in the CV itself.
